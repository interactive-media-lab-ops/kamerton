# КАМЕРТОН · правила розробки

## Проєкт і пріоритети

КАМЕРТОН — офлайн-односторінкове середовище підтримки рішень: щотижневий
зріз інформаційного поля для керівництва. Кінцевий продукт — один файл
`app/dist/kamerton.html`, який має відкриватися з диска через `file://` без
мережі, сервера й зовнішніх посилань.

Найважливіше: продукт не має домальовувати дані, підміняти оцінку фактом чи
робити хибний сигнал «зручнішим». Якщо виміру або верифікації немає, це має
бути явно видно в даних та UI.

## Незмінні правила роботи

- Компоненти не читають JSON напряму: вхід до контракту через
  `app/src/data/selectors.js`.
- Потік даних односторонній: `raw/` → builder → `derived/` → selectors/UI.
  Збірка не має записувати в `raw/`; зміна сирців — лише явна міграція або
  свідоме оновлення тижневого контракту.
- Одне число має одне джерело. Не дублюй числа, статуси чи правила в кількох
  модулях: ймовірність живе тільки у `Forecast`, а ринок посилається через
  `forecast_id`.
- Реєстр прогнозів append-only; невирішений прогноз не можна мовчки прибрати.
- Епістемічний статус — частина даних, а не декоративний стиль.
- Нові залежності, зовнішні запити, мережеві шрифти або CDN — тільки після
  рішення власника. Продукт повинен лишатися офлайн.
- Продуктовий бандл має ліміт 900 КБ (`scripts/check-invariants.mjs`; історія
  ліміту й виміряний розклад бандла в коментарі там само). Якщо запас
  закінчується, спершу прибирай дублювання даних через проєкцію, а не ріж
  зміст або валідацію.
- Не використовуй зображення реальних людей для інституцій чи аудиторій.
- У глибинному шарі не називати реальних людей міфічними героями й не
  діагностувати психотипи людей: це тільки аудиторні кластери.
- Розмітка має бути зрізана, якщо реакції поля немає; порожнечу не можна
  компенсувати вигаданим наративом.
- Тексти UI беруться зі спеки або погоджуються з власником. Не заводь
  механічні короткі імена в продакшн і не став довге тире в UI.
- Стан `draft` глибинної розмітки ніколи не показується. Виняток
  `draft_for_alignment` з видимим бейджем — чинне окреме рішення власника;
  не поширюй цей виняток на інші статуси. У звіт, як і раніше, йде лише
  `validated`.

## Команди

Усі команди запускаються з `app/`:

```bash
npm ci                 # чисте встановлення за package-lock.json
npm run check          # контракт, корпус, глибинний шар, карта, ансамбль
npm run build          # перебудовує app/dist/kamerton.html
npm run build:import   # окремо збирає importer у dist-import/
npm run qa:shots       # базові browser-скріншоти
npm run qa:plots       # живий QA вкладки «СЮЖЕТИ»
npm run qa:depth       # QA глибинного шару
```

Після зміни UI запускай відповідні QA-скрипти, а після зміни даних чи
селекторів — повний `npm run check`. `app/dist/kamerton.html` — згенерований
релізний артефакт: не редагуй його руками, оновлюй тільки через
`npm run build`.

Після будь-якої правки вкладки «СЮЖЕТИ»:

```bash
npm run check
npm run qa:plots
npm run qa:depth
npm run build
```

`npm run qa:f3` має застарілі текстові очікування від попереднього дизайну
режиму прецедентів. Не вважай його падіння дефектом глибинного шару; якщо
чіпаєш режим прецедентів, спочатку онови цей smoke-тест під чинний UI.

## Візуальна дисципліна

Пороги тримай у `src/data/config/thresholds.json`, а не в JSX/CSS. Карта має
нуль idle-анімацій; `prefers-reduced-motion` повинен давати той самий фінальний
стан. Постійних підписів на полотні — не більше чотирьох, світних вузлів — не
більше шести. Візуальні регресії часто ловляться лише живим Chromium QA, не
текстовими перевірками.

Не замінюй поведінку великим рефакторингом «для чистоти» без конкретного
дефекту чи задачі. Тут важливіші відтворюваність, чесність даних і візуальні
інваріанти, ніж абстрактна компактність коду.
